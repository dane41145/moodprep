# MoodPrep product memory

This file records established product behavior that must survive unrelated changes. Read it before changing MoodPrep. Update it when the user approves a new lasting behavior.

## Change-control rule

- Do not remove, hide, weaken, or silently replace any behavior listed here while implementing another feature.
- If a requested change conflicts with a recorded behavior, stop and ask the user which behavior should win before editing it.
- Refactors must preserve these behaviors and their data migrations.
- Verify affected behaviors with tests. A successful build alone is not enough.

## File workflow and safety

- Accepted processing replaces the image in its working folder immediately; there is no required export step.
- Before replacement, preserve the prior file in `moodprep-originals`. Preserve additional revisions with unique names.
- SVG sources convert to 2048 px PNG during intake and move to `moodprep-originals`.
- The render density for that conversion is derived from the SVG's own natural size, never fixed. A density is a resolution for the drawing's stated size rather than an output size, so no constant can be right for two files: the hardcoded 600 that stood here until 2026-09-06 asked librsvg for about 158 gigapixels from a seal declared at 535 mm, and 3.2 from the smallest logo in the collection. Every SVG threw `Input image exceeds pixel limit`, went onto `failed`, was left on disk as `.svg`, and was retried and failed again on the next launch — intake had been silently broken since at least late August, and all eight SVGs in the collection were affected. How the raster answers to the density is a property of the file and is measured rather than assumed: librsvg resolves a width in physical units (mm, pt, cm, in) through the density and libvips then scales that render by density/72 on top, so those files grow with the SQUARE of the density, while a unitless, px or percentage width grows linearly with it. `svgRenderDensity` in `electron/processor.ts` reads the longest side at the default density and again at twice it, takes the exponent from the two, and solves for the density that lands the longest side on 2048, rounding up so the PNG is a downscale rather than an enlargement. On this collection that is a density of 84 for the Philippines seal and 737 for a 200 px unitless drawing — the span no constant covers — and rasters of 1.6 to 4.3 MP rather than hundreds. Both reads are safe because the second only happens for a file already under the target. `SVG_MAX_DENSITY` binds only below about 60 px and exists to bound a file whose size scales in some way this has not measured. Guarded by `electron/svg-intake.test.ts`, which states the defect: its large-viewBox fixture is asserted to still throw at the old density before it is converted at the new one.
- A conversion that fails must say so where the failure lives, not only in a toast. A failed SVG is left on disk and retried on every scan, so the same files fail on every launch, and one line five seconds long in a message that begins `Indexed 1354 images` was the whole of the reporting — while the Collection sheet, which owns SVG conversion status, called those files `pending`, which reads as queued rather than as permanently broken. `convertSvgs` returns `failed` with a path and a reason each; `App` holds the last intake's failures and the Collection sheet's conversion panel names the files and their reasons and says they stay as SVG and are retried, instead of counting them as pending. Do not reduce this back to a count.
- The scan re-inspects only what has changed. Deriving one `ImageRecord` costs about four sharp decodes — thumbnail, perceptual hash, quality signals, rotation estimate — which measured 35 ms an image on this collection, so a folder of 1354 spent 48 seconds on every single launch re-deriving results that were already correct. `scanFolder` keeps them in `.moodprep/scan-cache.json`, keyed by absolute path with the file's size and mtime, and re-inspects a file only when either has moved: measured on the same images, a launch that changed nothing went from 46 s to under a second, and one changed file costs 58 ms. Both halves of the key are load-bearing — content can change without the size changing, and a file can be replaced with a different-sized one in the same instant — and a reused record must be byte-identical to a freshly derived one, which is asserted rather than assumed. `SCAN_CACHE_VERSION` is part of the stored file: anything that changes what `inspectImage` returns, a new signal or a different quality formula included, must bump it or the collection keeps showing scores computed under the old rule. `processed` is re-read on every scan rather than trusted from the cache, because it depends on the `moodprep-originals` folder rather than on the image, and it costs a directory listing rather than a decode. A missing, truncated, hand-edited or wrong-version cache is not an error — it only means this scan does the work — and a cache that cannot be written costs the next scan its head start and nothing else. The cache is derived data and lives beside the previews in `.moodprep`, never in `project.json`; it is about 13 KB an image, so roughly 18 MB for this collection. `ScanResult` reports `analysed` and `reused`, and the Collection sheet says which. Guarded by `electron/scan-cache.test.ts`.
- Previews are scratch and are pruned. Every revision writes a full-resolution file into `.moodprep/previews`, a commit re-encodes the chosen one into the source, and nothing ever pointed back at the rest — measured on 2026-09-09 the folder held 4,686 files and 5.8 GB with not one referenced by `project.json`, growing by up to a gigabyte a working day. `prunePreviews` in `electron/processor.ts` deletes every file in that folder not named in the list it is given; `App` calls it after every scan and whenever the workbench closes, passing the `outputPath` of every decision so a legacy preview-based edit is kept. It only ever touches files directly inside the previews folder, and a file it cannot remove waits for the next pass rather than failing the scan or the close. Do not make previews load-bearing across sessions without changing this. Guarded by `electron/prune.test.ts`.
- Do not mention SVG conversion in generic scan progress when no SVG-specific result is known. Report SVG conversion afterward only when files were converted.
- Confirmed exact duplicates are actually removed from the source folder after content verification; on macOS they go to Trash.
- An individual image can be removed from its working folder from the workbench only after an explicit confirmation; it moves to macOS Trash, while existing `moodprep-originals` references remain.

## Duplicate review

- `Replace original` is undoable rather than guarded by a confirmation dialog. It sits beside the routine per-group Apply buttons and is easy to hit by mistake, but it is reversible by design — the previous file is moved into `moodprep-originals`, not discarded — and for a reversible action undo is the standard answer: a dialog in front of a routine save is clicked through within a day and then stops catching the misclick it was added for. `revertCommittedImage` in `electron/processor.ts` is the exact inverse of `commitProcessedImage`, using the same rename dance so the replacement is only discarded once the backup is safely back in place, and it refuses a backup path outside `moodprep-originals`, a restore target inside it, and anything outside the project. The undo restores the decision as well as the file, because committing clears the issue tags and marks the image processed while a restored original still has whatever was wrong with it, and the library re-reads the file rather than patching the card. Guarded by `electron/revert.test.ts`, including the byte-for-byte round trip, repeated commit-and-undo on one file, and a stated failure when the backup has already been removed.
- A `Notice` is a message plus, when the action it reports can be taken back, the way to take it back; `setNotice` also accepts a bare string and wraps it, so the many plain notices did not have to change. A toast carrying an action lives 12 seconds rather than 5.2, and hovering holds it open — a toast that vanishes while the pointer is travelling towards its own Undo is worse than no undo at all.
- `Duplicate` in the workbench footer copies the open image to a sibling in the same folder named `<name> copy.<ext>`, numbering further copies rather than overwriting. It exists so one source can be taken in two directions — a different crop each, for example. The copy inherits the source's issue tags but none of its processed state, and it appears next to the original in the grid.
- A copy made that way is recorded with `duplicateOf` on its decision and is held out of BOTH exact and near duplicate grouping while its source is still in the collection. This is essential, not cosmetic: an exact copy would otherwise appear in the Exact copies tab with a Delete button and invite the user to destroy work they had deliberately forked. Other genuine duplicates in the same collection must still be grouped normally. Guarded by `electron/duplicate.test.ts` and the grouping tests in `src/utils.test.ts`.
- Duplication refuses paths outside the collection and anything inside `moodprep-originals`.

- Exact filename copies such as `file.jpg` and `file (1).jpg` should recommend the version without the numbered suffix when quality is equal.
- Near matches are suggestions only. Visually related brand artwork must be allowed to remain as distinct images.

## Issue tags

- Adding an issue tag in the workbench applies immediately: it is a cheap, reversible note.
- Removing a tag asserts that the issue does not apply to that image, which changes what the collection records, so it must be confirmed. Clicking an active chip arms a removal and shows an inline confirmation with `Keep it` and `Remove tag`; the tag stays until the confirmation is accepted. Clicking the same chip again, or `Keep it`, cancels. Clicking a different active chip moves the pending removal rather than removing anything.
- This confirmation covers deliberate deselection only. Tags that processing resolves are still cleared automatically, and a pending confirmation is dropped if its tag disappears that way.

## Processed-state behavior

- Every processed image must display a consistent `Processed` badge, including legacy preview-based edits and newer source-replacement edits.
- Resolved issue tags are cleared once after processing, so a processed image leaves filters such as Background. Fresh tags added later must survive rescans.
- Processing history must survive content-hash changes by using source-path and backup evidence.
- Reopening an already processed image must use the processed result as the working input, not the untouched original.
- Processing is continuous: every local or Gemini operation immediately becomes the next working revision, with no separate Preview, Discard preview, or Continue editing step.
- The workbench provides Undo, Redo, and Return to original across the current editing session. Undo and Redo are also bound to Cmd/Ctrl+Z and Cmd/Ctrl+Shift+Z (Ctrl+Y redoes as well), driving exactly the same history as the buttons. The shortcuts must never fire while the caret is in a text field, where those keys belong to the field's own undo; `undoRedoIntent` and `isTextEntryElement` in `src/utils.ts` enforce that and are tested. Applying a new operation after Undo drops only the abandoned redo branch.
- `Before`, at the end of the Undo / Redo / Return to original group, is a hold rather than a click: while it is held the stage shows the revision behind the working one, with the label `Before · revision N` (or `Before · original`), and releasing it puts the working revision back. It exists because comparing a result with what it replaced was being done with Undo and Redo, which is the wrong tool for a glance — each of those reloads the preview, resets every pending control, and any direct tool used in between (a fill, a stroke) drops the redo branch, so the result was sometimes gone by the time the user wanted it back (reported 2026-09-12; the history itself was verified sound in the renderer harness). Peeking moves nothing: the working revision, the redo branch and the pending controls are untouched, and crop, paint and the click tools are suspended on the stage while the previous picture is up so nothing can be drawn onto the wrong image. `peekRevision` in `src/utils.ts` decides what is shown; the editor keeps the last six editor previews in memory so the flick back and forth is instant. Space or Enter on the focused button holds it too. Guarded by the peek tests in `src/utils.test.ts`.
- Moving between revisions or applying a result resets local geometry/upscale controls to neutral values so operations are not accidentally applied twice.

## Local image tools

- The workbench shows one authoritative image preview on the left; controls must not add a duplicate image preview on the right.
- Cropping happens directly on the large left preview with draggable edges, corners, whole-frame movement, live percentages, and Reset. Crop is the default selection in the canvas tool strip, so the frame is present when the workbench opens.
- The crop frame is a sibling of the image canvas, not a child of it. The canvas clips its own overflow so paint strokes stop at the image edge, which also cut every handle in half; out here the handles sit wholly outside the frame with a 4px gap, clear of the artwork they are framing, and a frame at the image's own edge still shows all eight inside the stage's 32px interaction gutter — a 12px handle and a 4px gap is exactly the 16px that gutter gives each side. The frame's own edge is an `outline` with an outward `box-shadow`, never a `border`: under the global `box-sizing: border-box` a border is painted inside the positioned box and so covers the outermost two pixels of the crop, which was enough to make the top of a circle look cut off when it was only the marker. Nothing may be painted over the inside of the crop frame. The layer spans the whole image rectangle and must therefore stay `pointer-events: none`, with only `.crop-frame` and its handles taking input, or it would swallow the pointer starts the recorded capture behaviour depends on. The dimming outside the frame is four `.crop-shade` rectangles rather than one outward `box-shadow`: unclipped, a 999px shadow would dim the whole stage instead of the image. Crop is disabled whenever a rotation is pending, so the frame never needs the canvas's turn.
- The crop tool has a `1:1 square` lock, off by default, that constrains the frame to a perfect square. Crop insets are percentages of each axis, so a square in pixels is not a square in percentages — on the 2776 x 2443 coaster a 50% wide frame must be 56.8% tall — and `squareCropInsets` in `src/utils.ts` does that conversion in pixels for every drag. A corner drag takes the larger of the two candidate sides so the square encloses the pointer; a single edge drives its own axis and pins the edge that is not being held; switching the lock on squares the existing frame about its centre without growing past it. The lock is a mode, so it survives moving between revisions, and a whole-frame move needs no correction because it preserves the frame's size.
- The square must be exact, not approximately exact. Each inset rounds to pixels independently, which can land a locked frame on 1507 x 1508, so `ProcessRequest.squareCrop` makes the processor equalise the two sides to the shorter one, and `cropPixelSize` applies the same rule so the workbench's `Output … px` readout always states the size the saved file will actually have. Guarded by the 1:1 crop lock tests in `src/utils.test.ts`.
- The Replace tool draws its own icon rather than borrowing one. Lucide has no glyph for swapping one colour for another, and `Blend` — two thin overlapping circles — reads as decoration rather than a tool at the 16px the strip uses, so beside the crisp crop, brush, pipette and bucket shapes it looked like a missing icon. `ReplaceColour` in `src/App.tsx` says the operation in the same stroke language: the new colour chip laid over the old one.
- The five pointer modes — Crop, Paint, Pick, Fill, Replace — are mutually exclusive and are presented as one segmented tool strip with icons, above a single options block that shows only the active tool's controls. They must not be drawn as separate always-visible cards: only one can ever be live, and stacking them was what made the panel unreadable. Selecting Paint still switches Auto-trim and Centre content off; a pending rotation disables the whole strip with a stated reason.
- The controls panel is grouped under named headings — Canvas tool, Working colour, Straighten, Adjustments, Output — rather than a flat run of differently shaped cards. New local tools belong inside one of those groups.
- The left preview supports fit-to-window zoom from 100% through 400%, with scrolling and a dedicated high-resolution preview for genuine detail inspection rather than magnifying the card thumbnail.
- `Centre content` must automatically detect the current working image's dominant background color. White is not the unconditional default.
- The detected background color is visible in the picker. Manual selection overrides Auto; the Auto control restores detection.
- The `Working colour` block holds a colour chip that opens the system picker, a hex field with its own `#` affordance (typed without the hash), an `Auto` detect button, and a row of one-click presets. It is rendered once and shared by paint, fill, the straighten canvas fill, and centring; it must not be duplicated into individual tool cards. The hex field accepts `rrggbb` and 3-digit shorthand in any case; incomplete text is left alone while typing and reverts to the committed colour on blur. Choosing a preset or typing a code overrides Auto exactly like the chip does. Guarded by `normalizeHexColor` tests in `src/utils.test.ts`.
- The preset row always begins with pure white and pure black, then the four greys nearly every blank tee is stocked in, lightest first: ash `#dfe0e2`, athletic heather `#bfc1c3`, sport grey `#97999b` and dark heather `#3f4448` — so a design can be judged against the garment colour it will actually be printed on rather than only against the extremes. The two pale blanks were added on 2026-09-06; before that a design was never seen on the light shirts most of them are actually printed on. `GARMENT_COLOURS` in `src/App.tsx` is the one list, and the `from this image` label is placed at its length rather than at a counted index, so adding a garment colour cannot leave the label mid-row. White and black come first because those are the two values the rest of the pipeline leans on — a coaster isolated on black is swapped to white from here in one click. The image's own colours follow, introduced by a `from this image` label placed before them rather than trailing them, and deduplicated against white and black. They come from `detectDominantColors`, which delegates to the palette analysis rather than counting raw pixel buckets: on a flat two-colour design, bucket counting returns the ink followed by four shades of the anti-aliased ramp between ink and background, which are not colours anyone wants to paint with. Guarded by `electron/dominant.test.ts`.
- Background detection applies to chained/processed working images as well as originals.
- `Flatten colour noise` is a deterministic, no-API alternative for flat graphics. Its default is Auto: mathematically detect the smallest intended palette by clustering perceptually equivalent colours while discounting JPEG deviations and edge/anti-alias transitions. Detection and flattening are one analysis, not two algorithms: `analysePalette` in `electron/processor.ts` produces the swatches, and `mapToPalette` in `shared/palette.ts` snaps every pixel to the nearest of those swatches in Lab. It used to hand only a colour *count* to sharp's general-purpose quantiser, which minimises total pixel error and so spends its slots on the paper's gradient and merges the small inks — on the Jäcklein coaster a red and a green became one brown while the panel showed six swatches that included both. The analysis returns `candidates` (every distinct colour, strongest first, up to 16); a manual count of N flattens to the first N, so the picker can preview exactly what any count produces from one analysis, and counts beyond what was found are disabled rather than offered. Guarded by `shared/palette.test.ts` and the small-inks test in `electron/processor.test.ts`.
- Auto palette detection shows its inferred count and colour swatches for the current working image. Every integer from 2 through 16 remains available as a manual override when artistic intent differs from the estimate.
- Local preview generation remains deterministic and makes no external API call.
- `Rotate / straighten` provides deterministic manual correction across the range recorded below in 0.1° steps, previews the adjustment on the large image, expands the output rather than cropping corners, and fills newly exposed canvas with the selected background colour.
- The levelling grid is graph paper, not a lattice: fine 24 px squares with every fourth line kept strong, over the image's rotation envelope. 96 px squares alone were the first version and were too coarse to judge a degree by — the nearest line was usually far from the edge being straightened — while a fine grid with every line at the same weight reads as texture and hides the artwork. The fine lines therefore get their own much quieter pair of tokens, `--guide-line-faint` and `--guide-shade-faint`, and keep the same two-tone treatment (a light line with a dark companion below and right) so they stay visible over both pale board and dark ink.
- `Rotate / straighten` includes a deterministic Auto suggestion (no API call) that levels the artwork by projection-profile deskew: it searches for the angle that makes rows of text, banners, or an elongated subject align, which works on round coasters and badges where straight edges are scarce. Calibrated acceptance gates (score improvement ≥ 0.15, curve prominence ≥ 0.5, angle between 0.5° and 4.5°) reject ornament aliases and imperceptible corrections; artwork whose text sits only on arcs (for example the Hotel Plaza circular label) intentionally reports no confident tilt rather than a wrong angle. Auto only fills the rotation control (previewed live, manual slider still overrides); it never applies a revision by itself. Guarded by `electron/rotation.test.ts`, including the sign convention (a clockwise-tilted image gets a negative, counter-clockwise suggestion).
- `Rotate / straighten` offers 90° left and right quarter-turn buttons for orientation. A quarter turn applies the moment it is clicked and becomes its own revision, needing no Apply button of its own (changed 2026-09-06 at the user's request). It is the one rotation that costs nothing to commit — 90° is a transpose rather than a resample, so turning now and straightening afterwards still spends exactly one lossy resample, the same as the composed angle did — and holding it pending was what disabled crop, painting and recentre on an image the user had merely stood upright. It is refused only while paint strokes are pending, because applying a revision clears them and they would be lost rather than painted. The ±10° straightening slider is still pending and still needs Apply: it is continuous, and a second adjustment has to be read against the same base rather than compounding on the first. Composition is therefore gone; `composeStageRotation` and its tests are kept, unused, because the live-preview work may want them back and this repository has no version history to recover them from. Output dimensions guarded by `electron/rotation.test.ts`.
- The preview draws exactly one guide overlay at a time, chosen by the live tool rather than by a button. Cropping shows rule-of-thirds inside the crop frame; straightening shows the level grid over the image. Rotation disabling crop is not sufficient to keep them apart: the grid also appears while the `Straighten` group merely has focus, and at 0° the crop tool is still live, which put both on screen at once. `.crop-frame` therefore takes a `no-thirds` class whenever the level grid is up. Any future condition that shows the grid must go through that class too. The manual `Grid` toggle that used to sit in the quarter-turn row was removed for that reason: it was the only way to get both grids on screen at once, and its remaining job — a level reference at 0° — is now covered by the group's own focus. The level grid is visible whenever rotation or a quarter turn is non-zero, or while focus is anywhere inside the `Straighten` group (`onFocusCapture` / `onBlurCapture` on the group, with a `relatedTarget` containment check so moving between the slider and the degree field does not flicker it off).
- The level grid is a sibling of the image canvas inside the zoom space, never a child of it, so its lines stay true horizontal and vertical while the image turns — that is the whole point of the reference and must not regress — while still tracking the artwork when the stage is scrolled or zoomed. It is sized to the image's rotation envelope rather than to the whole stage: a grid over the empty surround around the image reads as texture rather than as a reference. Lines are 96px apart in `--guide-line-soft`, a step back from a single guide line because this one repeats across the whole image, with an emphasised centre crosshair.
- Every guide line on the preview — crop thirds and level grid alike — is drawn in one visual language from the `--guide-line`, `--guide-line-strong` and `--guide-shade` custom properties: a white hairline with a 1px dark companion offset below and right of it, so a guide stays readable over a pale label and over dark artwork alike. The crop thirds get their companion from a `drop-shadow` filter rather than a second element. New guide affordances must reuse those properties instead of inventing a second line treatment.
- A pending paint stroke carries the colour it was drawn in, on `PaintStroke.color`. Strokes used to be drawn in whatever the working colour was at render time, so choosing a second colour silently repainted every stroke already on the canvas: painting black and then red meant applying the black first and waiting for the whole pipeline before red could be picked. Several colours are now pending together and land in one pass — the stage previews each stroke in its own colour and the processor paints each in its own colour, falling back to the request's background for a stroke recorded before this existed. The single `Working colour` block stays shared by paint, fill, straighten and centring; it is the stroke that remembers, not the picker. Each stroke now lands on its own as the brush lifts, so it is painted in the colour it was drawn in by construction rather than by being remembered through a batch; the `color` field stays because a stroke can still be briefly pending while the previous one is in the pipeline, and because it is what makes the preview and the processor agree. Guarded by the two-colour stroke tests in `electron/processor.test.ts`.
- A small round icon button needs `padding: 0` written on it. A `<button>` carries the browser's own `1px 6px`, and on the 21px `.select-check` circle that left a 7px content box for a 14px tick: a grid item wider than its track is aligned to the start rather than centred, so the tick sat 3.5px right of the middle of the circle — visible, and reported as such. `place-items: center` does not save you; the padding has to go. Measured rather than eyeballed: the button's centre and the icon's centre now agree exactly. The other small icon buttons (`.stage-zoom-controls button`, `.rotation-tool > button`) have content boxes wider than their icons and are genuinely centred, so this is not a blanket rule to apply everywhere — it is what to check first when an icon looks a pixel or two out.
- A pending rotation disables crop and background painting until it is applied or reset, because a rotated canvas rectangle no longer maps to source pixel coordinates. Only the ±10° slider can be pending now — a quarter turn applies immediately and leaves nothing to block.
- Scanning tags images whose confident suggestion is non-zero with the `rotation_needed` issue ("Rotation Needed"). Project version 4 migration unions only this fresh tag into stored decisions once, so tags the user removed for other issue types stay removed. Opening a tagged image in the workbench pre-fills the suggested angle the way border/off-centre tags pre-fill their controls; the tag clears after processing like every resolved tag.
- Paint, Pick, Fill and Replace are direct tools and none of them has an Apply. Paint was the last one to still batch, and its button was removed on 2026-09-08 at the user's request: a brush is a direct tool, so pointer-up is the commit, exactly as a click is for Fill. Each finished stroke becomes its own revision and Undo takes back one stroke at a time — measured in the real renderer, one drag produces one `processImage` call carrying one stroke, and Undo walked 8 → 7 → 6 revisions. The full-screen busy overlay is deliberately NOT used for a stroke: it would flash on every one. The stroke stays drawn on the preview until its revision arrives, which is the same picture either way, so there is nothing to see. Runs are serialised rather than fired blindly — painting is quick and the round trip is not — so a stroke drawn while one is still in the pipeline is picked up by the next run instead of racing it from a stale base; `paintStrokesRef` is kept exact rather than a render behind, because the flush reads it inside a promise callback where React state is still the previous value. Only the strokes that were sent are cleared when a run returns. Measured with a 250 ms pipeline: four rapid drags produced four serialised runs and lost nothing.
- `Pick & fill` provides an eyedropper and a paint bucket beside the brush. Pick, Fill and Replace share one cursor family: the hotspot is the centre of a crosshair, with the tool glyph offset clear of it, which is how every paint application marks a precise click point. Glyph-only cursors were the previous treatment and put the hotspot in empty space beside the artwork — the Fill hotspot sat below and left of the bucket outline, touching no ink at all, which left the exact fill point to guesswork. Both the crosshair and the glyph are drawn dark-then-white, the same two-tone treatment the preview guides use, so a cursor stays visible over a pale label and over dark artwork alike. Pick reads the true pixel colour from the working file rather than from the on-screen JPEG preview, so a sampled colour matches what a fill will match against; it commits that colour as the background/fill colour, overriding Auto, and disarms itself after one pick. Fill floods the contiguous region around the click within a user-set match tolerance; contiguity is the safety property, since a tolerance wide enough to swallow a photographed surround would otherwise also change matching tones inside the artwork. Each fill immediately becomes its own working revision so Undo steps back one fill at a time, and the view the user is working at survives it because filling is a click-repeat tool — see the view-preservation rule below, which replaced the hand-rolled zoom save and restore that used to sit in the fill handler. Painting, picking, and filling are mutually exclusive, and all are unavailable while an unapplied rotation is pending. The fill colour is set three ways that all edit one value: the eyedropper, the native colour swatch, and a typed hex code. It is rendered once, in its own `Working colour` group directly beneath the tool strip, and is shared by paint, fill, the straighten canvas fill, and centring; it must not be duplicated into individual tool cards. Guarded by `electron/fill.test.ts`.
- Neither `Fill` nor `Replace` can leave a fringe of the colour it replaced, and the Match slider is not the answer to one. The pixels where the old colour meets the artwork are a blend of the two, so a tolerance wide enough to include a half-covered pixel is also wide enough to include the artwork: measured on the Goodheart's Laundry heart, replacing white with black at Match 12 left a pixel of (226,173,157) completely untouched as a pale halo along the whole silhouette, at Match 40 it went grey rather than dark red, and at Match 80 the halo cleared only because the heart's own red had been darkened by 40%. The blend does not need matching, because it is a known quantity: for a pixel that is artwork colour C over old colour B at coverage a, the same artwork over T is `out = P + (1-a)(T - B)`, so only the share of B is recovered and the artwork colour is never touched. `shared/fringe.ts` holds it, driven by whatever mask the fill produced — the flooded region for the bucket, the matched pixels for the global replace — so both scopes get the same clean edge; `shared/backdrop.ts` makes the same argument for the frame-connected surround and is left alone. Coverage is the projection of the pixel onto the line from B to a local reference colour, and the reference is chosen as the neighbouring solid colour whose line passes closest to the pixel rather than the most different one nearby: gold lettering and red artwork meeting the same white background is a three-colour edge, and reading the gold against the red would smudge it. A pixel more than a quarter of that line's length off it is not a blend of the two and is left alone. On the heart the most white left standing anywhere fell from 212 to 32, and the correct answer for a 64%-covered edge pixel is (125,43,27), which is what it now produces. Guarded by `shared/fringe.test.ts` and the halo tests in `electron/fill.test.ts`.
- `Replace` is the global-scope companion to the contiguous `Fill`: clicking a colour swaps it for the working colour across the entire image at once. Flat two-colour artwork keeps that colour in many disconnected pockets — inside letters, between rings, outside the disc — so a bucket alone cannot do the job and clicking each pocket is unusable. Both scopes share one request type; omitting the scope means contiguous.
- `Paint with background` shows the live brush footprint on the large preview, supports circle and square brushes, and is sized in source pixels down to a single one, because touching out a speck is what the smallest sizes are for. Size is stored as a fraction of the image's shorter edge so it survives a change of revision and a resize, but it is chosen and displayed in pixels. The slider track is logarithmic — a linear pixel track would spend almost all its travel on sizes nobody uses — running from 1px to 16% of the shorter edge. Below about nine screen pixels the footprint is too small to aim with, so the preview falls back to a fixed-size crosshair the way precise cursors do in every paint tool. Guarded by the brush sizing tests in `src/utils.test.ts`, including the one-pixel floor, the share of travel given to fine sizes, and stability of the stored fraction across a resize.
- `Paint with background` must work at every image edge and corner. While painting is active, incompatible Auto-trim and Centre content operations are turned off so painted edge pixels cannot be cropped away.
- The toast is a wide, slim bar centred at the very bottom of the window, in both the library and the workbench. It used to move to the workbench's lower left while the editor was open, where it covered the footer's quality readout and revision hint for the whole of its life — twelve seconds for an undoable one. Only notices without an action give up their pointer events over the editor; a toast carrying `Undo` must stay clickable, and a dead button is worse than an obscured readout. The commit notice names the file once and the backup folder without repeating the path, because these filenames are 32-character hashes.
- Workbench notifications must never intercept or visually obscure pointer input over the large preview; hide them while background painting is active.
- Background painting captures pointer input directly on the image's complete screen-space rectangle with pointer capture, so strokes continue cleanly through a drag.
- While painting is active, a dedicated interaction layer tracks the currently visible image rectangle above non-interactive stage content. Painting must not depend on the image element winning browser hit-testing against sibling overlays; Undo and zoom controls remain above the capture layer.
- Crop and background-paint interactions must capture pointer starts against the image rectangle before overlapping renderer layers can consume them. Every crop handle and every paintable image region, including the lower-left, must be able to begin an interaction as well as receive a continued drag.
- Zoom changes the image canvas's real layout dimensions rather than visually scaling a smaller hit target. Zoomed canvases keep a reserved interaction gutter between every image edge and native overlay scrollbars, so the bottom edge and lower corners never sit beneath a scrollbar dead zone.
- A pointer START belongs to the image only if it lands on the part of the image that is on screen, and that is a different rectangle from the canvas. The stage installs a document-level capture-phase `pointerdown` listener so a crop or paint start wins against overlapping renderer layers, and until 2026-09-07 it decided ownership by testing the pointer against the canvas element's `getBoundingClientRect`. That is the canvas's whole layout box: the viewport clips what is drawn but does not shrink the box, so above 1x it runs hundreds of pixels past the viewport and straight across the controls panel, the footer and the toast. Every start landing there was claimed, `preventDefault`ed and `stopImmediatePropagation`ed, and React never saw the click — and because Crop is the default tool, this was the default state of the workbench. Measured in the real DOM on a 736 x 730 label in a 1400px window: the canvas reaches 43px past the viewport at 125%, 190px at 150%, 337px at 175% and 1657px at 400%; the colour chip and the garment presets died at 150%, the hex field at 175%, and by 350% the tool strip and `Replace original` were dead too. That is the whole of the reported "you can't change colors" and the "host of other issues" with it — one cause, not many. Worse than dead: with Fill or Replace armed the same click ran a flood fill on the image, because the claimed start went to `onSample`. `visibleImageRect` and `pointerOverVisibleImage` in `src/utils.ts` hold the rule, the capture layer and the hit test now share that one definition of visible, and the gate is the first thing `pointerDown` does — nothing is claimed, prevented or stopped above it. Mapping a point onto the image is deliberately still done against the whole canvas: once a stroke or a crop drag is under way the pointer may travel outside the visible area and must still map to the right pixel and clamp at the image's own edge. Guarded by the zoom hit-testing tests in `src/utils.test.ts`, which state the defect as well as the fix.
- The view survives a revision. Zoom and scroll position are how the user is looking at the image, not operations on it, and neither is ever sent to the processor, so neither is reset by one. Before 2026-09-06 both were: the stage re-centred its scroll whenever the preview data URL changed, and `resetOperationControls` set the zoom back to fit, so every fill, every applied batch and every Undo threw the user out to fit-to-window and the middle of the canvas — worst on exactly the click-repeat tools you zoom in for, and it made Undo and Redo close to unusable above 100%. Fill had a hand-rolled zoom save and restore to work around half of it, which is gone. Placing the view is keyed on the shape of the scrollable space (`geometry.spaceWidth`/`spaceHeight`) and never on the preview, so only a change that actually moves the artwork under the viewport — a new zoom, a resized window, a revision with new dimensions — re-places it, and it is re-placed where the user was. The remembered position is a fraction of the scrollable space on each axis rather than a pixel offset, because a revision can change the image's dimensions and the same fraction still frames the same part of the artwork; an axis with nothing to scroll reads as the middle, which is what keeps fit-to-window and back a recentre. `stageViewFraction` and `stageViewOffset` in `src/utils.ts` hold it. Guarded by the view-preservation tests in `src/utils.test.ts`.
- Pending background-paint strokes use the workbench's main Undo, Redo, and Return to original controls. There is no separate competing stroke-history interface, and a new stroke after Undo drops the abandoned stroke redo branch.
- The top bar's left padding exists to clear the macOS window buttons. `titleBarStyle` is `hiddenInset`, so the traffic lights are drawn over the top-left of `.topbar`, and at the old 22px they sat on top of the MoodPrep logo. Any change to that padding must keep the logo clear of them.
- `src/window-drag-regions.test.ts` reads selector text from a comment-stripped copy of the stylesheet. The pattern that finds a drag rule's selector spans newlines, so a comment written directly above such a rule would otherwise be swallowed into the selector and fail the test for no real reason.
- Native window-drag regions (`-webkit-app-region: drag` on the top bar and the welcome header) are resolved by the OS from geometry alone, so dialogs stacked above them cannot block window dragging: a mouse press there moves the window and never reaches the page. Every full-window overlay (`.modal-backdrop`, `.busy-overlay`) must declare `-webkit-app-region: no-drag` so workbench input — including crop handles and paint starts over the preview — is never swallowed while a dialog is open. Guarded by `src/window-drag-regions.test.ts`; any new full-window overlay or drag region must keep that test honest.

- Every local operation has its own Apply, and there is no global one. `Apply local changes` was removed on 2026-09-08 at the user's request: with Undo and Redo covering the risk it was a confirmation of a decision already made, and because it ran thirteen unrelated settings at once, pressing it could not be predicted from any single control on screen. Each tool group that needs one ends with its own button — `Apply crop`, `Apply rotation`, `Apply adjustments`, `Apply resize` — disabled until that group has something waiting. `applyStep` in `src/App.tsx` is the one path: fields the caller does not name default to neutral, so a step can never carry a setting from a group the user was not applying, which is asserted rather than assumed. Fill, Replace and quarter turns still apply on click and need no button at all.
- A revision clears what produced it and nothing else. This is what makes a button per group work: applying a crop must not throw away the rotation you had dialled in, so `addRevision` takes the reset for the step that made it. `resetCrop`, `resetStraighten`, `resetPaint`, `resetAdjustments` and `resetOutput` are separate, moving between revisions is the one case that still clears everything — the base every pending control was measured against has been swapped out — and Fill, Replace and a reconstruction consume no pending control so they clear nothing. `squareCrop` and `paletteMode` are absent from every reset because they are modes rather than pending operations, and a mode survives.
- The straighten slider runs ±45° in 0.1° steps, widened from ±10° on 2026-09-08 so a piece photographed properly askew can be brought upright without spending a quarter turn first. `ROTATION_LIMIT` in `src/utils.ts` is the single value; the processor already accepted anything up to ±180, so this is the renderer's limit alone. Past 45 a quarter turn is the shorter way round and those are their own buttons. `detectRotation`'s acceptance gates are deliberately unchanged at 0.5°–4.5°: they were calibrated by measurement against real coasters, and widening them without measuring again would only produce confident wrong answers. Guarded by the straighten range tests in `src/utils.test.ts`.

## Library shell and ordering

- The application is one library screen, not a numbered wizard. The three-step Intake / Duplicates / Process sidebar was removed on 2026-08-31 because it spent a permanent 238 px column on navigation between stages that were never actually sequential. Do not reintroduce step navigation; a new capability becomes a control on the library or a sheet opened from it.
- Every function the steps used to hold stays reachable in one click and must not be dropped when the shell changes: intake statistics, the format breakdown, the ignored-file count, `Include subfolders`, rescan, and SVG conversion status live in the **Collection** sheet; exact/near tabs, keeper choice, `Apply all recommendations`, `Keep all as different`, and `Delete confirmed copies` live in the **Duplicates** sheet; search, issue filtering, bulk tagging, and the image grid are the library itself.
- Both sheets open over the library as `.modal-backdrop` dialogs rather than replacing it, so the grid is always one dismissal away. Reusing that class is what keeps them covered by the drag-region rule above.
- Quick filters (All images / Needs work / Processed / Untouched) double as the collection's headline counts, and the exact-copy and near-match counts beside them open the Duplicates sheet on the matching tab.
- The library sorts by Name, Date Added, Date Modified, File Size, Dimensions, Quality, and File Type, in either direction. `modifiedAt` and `addedAt` are captured on `ImageRecord` at scan time; a filesystem that reports no creation time falls back to the modification time, and a record with no usable timestamp sorts as unknown rather than as 1970.
- Every sort falls back to a numeric-collated name comparison, so equal values keep a stable order instead of shuffling between renders, and `scan 2.jpg` stays ahead of `scan 10.jpg`. Choosing a key resets the direction to that key's natural reading order — names ascend, dates and sizes lead with the newest and largest.
- The grid mounts a window of the filtered list rather than all of it, `GRID_PAGE` (120) at a time, extended by an `IntersectionObserver` sentinel 600 px before the end and reset whenever the filter, search or sort makes a new list. Every card carries its thumbnail inline as a data URL, so the whole collection at once was 16 MB of DOM: measured on 1352 images, `innerHTML` alone took 1018 ms and the forced layout another 218 ms, before the browser had begun decoding 1352 JPEGs — the first painted frame had still not arrived after 76 seconds. A screenful at a time is 163 ms. Only the DOM is windowed: filtering, sorting, the counts, `Select all`, shift-click ranges and bulk actions all still run over the whole filtered list, and they must continue to. `content-visibility: auto` with `contain-intrinsic-size: auto 256px` on `.image-card` does the rest, letting the browser skip layout and paint for a card scrolled out of view — that alone took the forced layout from 218 ms to 22 ms. 256 px is the card's measured height at the grid's column width; `auto` replaces it with the real one after a card has rendered once.
- The image card's secondary line shows the value being sorted on (a date when sorting by date, a byte size when sorting by size), so the order on screen is always readable rather than implied. Guarded by the sorting tests in `src/utils.test.ts`.
- The chosen sort is a per-machine working preference in `localStorage`, never written into the folder's `project.json`.
- Selecting images is for acting on them, and every action a selection allows is visible in the bulk bar: the count, `Select all N` and `Clear`, the tags, and `Delete N…` at the far end in the destructive colour. Before 2026-09-06 the bar held a count, nine identical grey tag buttons and an unlabelled ×, and there was no way to delete a selection at all — deleting four images meant opening each one in the workbench and confirming four native dialogs. Do not let an action be reachable only one image at a time again.
- A tag in the bulk bar is a three-state control — every one, some, none — and pressing it ends in that state on every selected image: on, unless it was already on all of them. The old behaviour toggled each image independently, which on a mixed selection swapped which images carried the tag and left it just as mixed, with nothing on screen saying which state you were in. `bulkTagState` and `bulkTagAction` in `src/utils.ts` hold it. Guarded by the bulk selection tests in `src/utils.test.ts`.
- Building a selection is a keyboard and modifier job, not one click per card: shift-clicking a checkbox selects the range between it and the last one touched, in the order the grid is showing (`selectionRange`), ⌘/Ctrl+A selects everything currently shown, and Escape clears. All three stand down while the workbench is open, which owns the keyboard.
- A selection can outlive the filter that made it, so the bar says when it holds images the grid is not showing (`N not shown here`) and offers to drop them. A bulk action that silently reached images the user could not see would be unsafe for deletion above all.
- Bulk deletion asks once for the whole batch. `delete-images` in `electron/main.ts` names the files in one native confirmation, then trashes them with `shell.trashItem` behind the same `assertInsideFolder` guard as every other write, and reports what failed rather than throwing the batch away. Looping the single-image handler would stack one dialog per file, which is not a bulk action. Removed images leave the collection in one state update, not one per file.

## Language

- The interface is available in English and Simplified Chinese, chosen in Settings and applied the moment it is chosen. The choice is a per-machine working preference in `localStorage` (`moodprep.language`), like the sort order, never written into `project.json`. `src/i18n.ts` holds the mechanism: dictionaries are keyed on the English text itself (`src/locales/zh.ts`), `t(key, vars)` fills `{name}` placeholders, and a key with no entry falls back to the English so a missing translation is a visible English string rather than a blank. `src/i18n.test.ts` scans `src/App.tsx` for every `t('…')` key plus every label that comes from data (issue tags, quality bands, sort options, presets, models, backdrops, regions) and fails on any the Chinese dictionary does not carry, and it checks every translation keeps the placeholders its English key has. Plurals are two keys (`'{n} exact copy'` / `'{n} exact copies'`) chosen in the component; Chinese maps both to one form.
- The native delete confirmations follow the language: `delete-image` and `delete-images` take an optional `DeletionLabels` object from the renderer (title, message, detail, cancel, confirm) and keep their English defaults for a caller that sends none.
- The preset prompts and the prompt-author instruction are written in the interface language, so a user who reads only Chinese gets a prompt they can read and edit. `src/prompts.zh.ts` mirrors the English builders paragraph for paragraph and carries the same load-bearing sentences — the six-measurement test, the rigid-group instruction, "concentricity wins", "move and do nothing else", the square-frame demand, the substrate-only de-yellowing — and `backdropPhrase(id, language)` in `src/utils.ts` gives the surround phrase in the prompt's language (None is null in both, dropping the paragraph). The Chinese author instruction asks for a Chinese reply and the Chinese closing sentence, and `cleanAuthoredPrompt` strips Chinese preambles and 「」 quotes too. Anything measured in the English prompts was measured in English: a Chinese prompt is a translation, not a re-measurement, so a difference in model behaviour between the two is worth checking before blaming the wording. Guarded by `src/i18n.test.ts`.
- What is NOT translated: error messages raised inside the Electron process (network failures, API errors, path guards) and the processor's quality *reasons* travel as English data; the renderer translates the known reason shapes (`translateQualityReason`) and shows anything else as it came. Provider names (Gemini, Qwen) and model ids are left as they are.

## Gemini behavior

- Gemini reconstruction is optional and only runs when explicitly triggered.
- The API key is stored using the operating system's secure storage, not in the project folder.
- The current image model is `gemini-3.1-flash-image`.
- Gemini reconstruction defaults to 1K; 2K and 4K remain explicit choices.
- Not every model serves every output size, and this is the single most confusing failure the app has had. Measured against the live API on 2026-09-06: `gemini-3.1-flash-lite-image` returns 1K and answers a 2K or 4K request with **HTTP 404 `Requested entity was not found`** — an error that names nothing, reads like a retired model id, and sent the user looking for a prompt that was too long. `gemini-3.1-flash-image` and `gemini-3-pro-image` served 1K, 2K and 4K. It is nothing to do with the prompt: the 8,558-character `Photographed coaster` prompt succeeded on Flash Lite at 1K, and the 649-character `Complete edges` prompt failed on the same model at 2K. Prompt length has never been the variable; output size is. `AiModel.sizes` in `shared/models.ts` records this, and it is measured data rather than documentation — re-measure it before changing it.
- A preset's `minSize` decides which models it can be sent to. `Complete edges` and `Photographed coaster` need 2K because their sources are around 3000 px, so Flash Lite cannot run either of them, and it is therefore dropped from the model menu rather than offered and then failing — those two default to Flash. Every other preset floors at 1K and keeps Flash Lite as the default. The dependency runs one way: the size is what the work needs, and the model follows it. `modelsForSize` builds the model menu from the size currently selected, `modelForSize` moves off a model that cannot serve a newly raised size (keeping the user's provider where that provider has something suitable, so raising the size does not silently move a Qwen user to Gemini), and the size menu starts at the preset's floor. Before this the app offered every model at every size and hardcoded the 2K bump for two preset ids, which is what let the default model be paired with a size it cannot serve. Guarded by the size tests in `shared/models.test.ts` and the preset/model tests in `src/utils.test.ts`.
- Policy blocks must be described as Gemini declining an image, not as a broken API key or generic network failure.
- Users must be warned that generated edits can alter text, spelling, proportions, and line work.
- The `Photographed coaster` preset must correct the printed original's own geometry, not only the camera's. Vintage coasters were printed on fast presses and are genuinely out of register, so the inner disc really does sit off-centre inside the outer ring on the physical object — asking for symmetry and for fidelity to the reference in the same prompt let fidelity win, and results came back faithfully lopsided, which is useless on a T-shirt. The prompt therefore carries a dedicated `Concentricity and ring placement` paragraph that names that case, requires one shared centre for every concentric element, states the measurable test (the band between neighbouring rings measured at top, bottom, left, right and both diagonals must be equal), demands equal black margins on all four sides, and says in both places it could be misread that geometry outranks fidelity: fidelity governs wording, illustration, typography and colour, never where a ring sits. Guarded by the concentricity and centring tests in `src/utils.test.ts`.
- The `Photographed coaster` preset must confine its age correction to the substrate. Gemini de-yellows aged board correctly, but was applying that correction globally, and subtracting yellow across the whole frame is exactly the operation that turns a vermilion into a plain red and a coral into a crimson — the wanted correction was eating the ink colours. The prompt therefore carries a `Colour` paragraph that scopes the de-yellowing to areas that were originally white, cream or near-neutral, forbids a global white balance, cast removal, rebalance or desaturation by name, states the mechanism so the rule cannot be mistaken for a general instruction to leave colour alone, and pins the specific hue shifts seen on real coasters: vermilion stays orange-red, coral and pink must not deepen into crimson or maroon, a warm colour is never treated as a faded cool one, and the palette must not be muted or harmonised. The `Condition` paragraph's damage list previously licensed exactly that global correction and now scopes its colour cast to neutral areas; the two paragraphs must not be allowed to contradict each other again. Guarded by the ink-colour tests in `src/utils.test.ts`.
- `Replace backdrop` swaps an already-isolated surround for the working colour, and it is a re-composite rather than a fill. Flooding the surround leaves a thin line along every edge, because the pixels where artwork meets surround are a blend of the two and no tolerance is both wide enough to catch them and narrow enough to spare the artwork. They do not need catching: for a pixel P that is artwork C over surround B at coverage a, putting the same artwork over a new surround T gives `out = P + (1-a)(T - B)`, so only the coverage has to be recovered, never the artwork colour. Coverage is measured against a local reference taken just past the blend, so a pale edge and a dark edge each get their own. `shared/backdrop.ts` holds it; the surround is read from the frame's corners rather than assumed, only the region connected to the frame is touched — a dark area enclosed by the artwork stays put — and it carries the same leak guard as the isolation pass, declining rather than blanking the image if the flood reaches the middle. Guarded by `shared/backdrop.test.ts`, whose central test walks across the join and asserts no pixel is left darker than either side.
- The surround colour is a prompt decision, not only a post-process. `AI_BACKDROPS` in `shared/models.ts` offers None (default), black, white, the four tee greys — ash, athletic heather, sport grey, dark heather, lightest first, the same set and order as the working-colour presets — and Auto, and every preset that produces a surround names the chosen colour in its prompt — telling the model to return black and then forcing another colour afterwards means re-compositing edges against a colour the artwork was never composited over. `Complete edges` and `Custom` are excluded: the first continues the artwork's own background outwards, so naming a backdrop would contradict the one thing it exists to do. Auto has no hex, so the deterministic isolation pass is skipped for it — there is nothing to enforce when the model chose the colour. Changing the backdrop rewrites the prompt, exactly as changing the preset does. `None` is the default and is not a colour: its `phrase` is null, the surround paragraph is dropped from the prompt entirely, and nothing in the request asks for the background to change — the user reversed the black default on 2026-09-05 because most presets should not be recolouring a background unasked. The coaster preset is the exception that still has to say something, since removing the photographed table leaves a hole: under None it asks for `a single flat colour` and names none. Dropping a paragraph leaves the double space where it was, so `buildGeminiPresetPrompt` collapses runs of spaces before returning. The choice is made from a left-to-right row of colour squares beside the model menu rather than a dropdown — the value is a colour, so the control shows the colours; None is an empty square with a diagonal strike and Auto is a spectrum disc, both of which read as "not one of these swatches" without a label. Guarded by the None tests in `src/utils.test.ts`.
- `Recentre inner content` was deleted on 2026-09-06 and replaced by the `Even the border` Gemini preset, at the user's request: it never worked in practice. It was a deterministic tool — a dashed ring dragged on the preview, the artwork inside it moved bodily, the crescent behind it closed with the ring's own colour sampled per angle — and the record of why it could not be made to work is worth keeping, because it is the argument for reaching for the model here. It had no `Auto`, and that was a finding rather than an omission: four detection methods were built and measured against two real coasters — four-cone probing with a global ring colour, the same with per-ray colours, a full 360-degree trace with a robust circle fit, and narrow cardinal cones with a step-edge detector — and each got one of the two backwards, because the Ihring coaster's cream ring blends into cream areas of the illustration at every angle but one scanline. Circularity was not a usable confidence signal either: the oval that worked scored 10.9% residual against the circle that failed at 3.1%. That left it manual, and manual meant the user judging a ring width by eye and finding, on the Neuweiler coaster, that only rings of 347 or 348 px kept every colour sample on the band — a four-pixel window, on one image. A tool with a window that narrow is a tool that does not work. Do not reinstate a deterministic version without measuring it against the Ihring case first; the model does not need the ring, the sample or the window.
- `Even the border` is the Gemini preset that took its place. It is a single-job preset in the mould of `Clean edges`, and it carries no surround, no issue tags and no fidelity paragraph for the same reason: it moves one shape and must not be handed a licence to redraw anything, so it also disables the backdrop squares. Two things in it are load-bearing and were learned from the coaster preset. It states a measurable test rather than asking for centring — the band between the shapes measured at top, bottom, left, right and both diagonals, all six equal — because "centre it" is what the model already believes it is doing. And it says in as many words that the regularisation outranks the reference: asking for symmetry and for fidelity in the same breath is what returned faithfully lopsided coasters, so it states that the piece really is out of register, that reproducing that is what is not wanted, and that concentricity wins. It also asks explicitly for the vacated space to be closed with the surrounding colour, leaving no seam, halo or ghost — the one thing the deterministic tool did well and a model will happily leave behind. On 2026-09-14 the Dominion Brewery XXX Porter roundel came back from it with its inner disc, rings and lettering exactly as off-centre as they went in: the old wording said only "one shape sits inside another", left the model to decide what the shape was, and its change-nothing paragraph won. The prompt is now procedural — find the outer silhouette's centre, treat everything inside the outermost band (rings, bands, curved lettering, central panel, every printed element) as ONE rigid group, translate that group until the centres coincide, nothing inside it shifting relative to anything else — and it says in as many words that returning the image with the offset it arrived with is the specific failure it exists to prevent, that the bands must be measured before answering, and to move again if they are unequal. The coaster preset's `Concentricity and ring placement` paragraph carries the same rigid-group instruction and the same named failure. Guarded by the `even the border preset` and coaster concentricity tests in `src/utils.test.ts`.
- `Add border` in `Adjustments` frames the artwork in the working colour. It extends the canvas outward rather than painting over the edge, so no artwork is covered and the saved file grows on both sides of each axis. The width is stored as a share of the image's SHORTER edge — the convention brush size set — so it keeps its proportion across a revision, a crop and an upscale instead of being a pixel count that means something different on every image; it is chosen and displayed in pixels, as brush size is. The shorter edge rather than the width, the mean or the diagonal, because a uniform border is bounded by the dimension it can most easily overwhelm: on a 3000 x 600 banner a border measured off the mean would eat a quarter of the height while looking modest across the top. The default is 4% — 29 px on a 736 x 730 label, 98 px on a 2776 x 2443 coaster — which reads as a frame at a glance without becoming the subject; the range is 0.5% to 20%, and at the maximum the two borders together are still under half the shorter edge. In the pipeline it goes last, after the upscale so its width is real output pixels rather than the upscale's multiple of them, and after the palette flatten so the colour that lands is the one that was picked rather than whatever the quantiser rounded it to. It uses the shared working colour and must not grow a colour control of its own. It carries a slider, so it is committed by the `Adjustments` group's own Apply rather than on click. `borderPixels`, `borderedSize`, `borderFromPixels` and `clampBorder` in `src/utils.ts`; guarded by the border tests in `src/utils.test.ts` and the pixel-level framing tests in `electron/processor.test.ts`, which check the corners and edges are exactly the chosen colour and the artwork underneath is untouched.
- The working-colour preset row carries two key colours after the garment blanks, introduced by a `for keying a fill` label: `#ff00ff` magenta and `#00ff00` green. They are not garment colours and must never be treated as one — `KEY_COLOURS` is its own list in `src/App.tsx`, and the `from this image` label is placed at `GARMENT_COLOURS.length + KEY_COLOURS.length` so adding to either list cannot leave a label mid-row. They exist because swapping one colour for another is unsafe when the first also appears somewhere that must not change: fill the region with a key first, which nothing in a vintage printed label can match, then `Replace` that key globally with the colour actually wanted. Two rather than one so there is always an unused key if the artwork happens to contain the other.
- `Recolour` is a deterministic local adjustment in the `Adjustments` group, not a Gemini preset. It was tried as a prompt first and that was the wrong tool: the job is a colour transform, so it needs no model, no API call, no wait, and no chance of the drawing coming back altered. `shared/recolour.ts` holds the whole of it, pure and shared by the processor and the renderer. Every hue keeps its identity and moves only to another shade of itself — a red returns a red, a pink a pink — enforced by a hue ceiling of half a control spacing less a degree, so a hue can never reach its neighbour's centre. The expressive range therefore lives in saturation (±0.34) and lightness (±0.16), neither of which touches hue identity; the earlier, smaller values made several variations indistinguishable from one another. Most of each shift is common to every hue so the intervals between colours survive and the result reads as one deliberate move rather than noise, with the remaining 35% jittered per hue. Twelve control points are interpolated into a 360-entry table so a gradient crossing a boundary does not band, and the neutral exclusion — blacks, whites, greys, near-black linework, near-white paper and the background — eases in rather than switching, because a hard cutoff leaves a coloured fringe on every anti-aliased edge and these files are usually converted from SVG. The eight variations step through golden-ratio sequences rather than a hash, which spreads them evenly instead of letting two land on the same scheme by chance; the same variation and amount give the same image every time, on every machine. Guarded by `shared/recolour.test.ts`, including family containment at full strength, interval preservation, continuity across the 359→0 seam, and the neutrals being returned untouched.
- Reconstruction is multi-provider. `shared/models.ts` is the single registry of what can be sent to; `gemini-3.1-flash-lite-image` is the default because it is roughly a third of Flash's price and these are small flat graphics rather than photographs. Gemini Flash and Pro are there for what Flash Lite cannot hold, and `qwen-image-edit-plus` is there because it keeps printed lettering more faithfully than anything else at that price — which decides it for a library of German blackletter, French, Thai and Bengali where every prompt demands the original wording back untouched. An unknown model id falls back to the default rather than reaching an API.
- The two providers share only the pre-processing (edge extension, square padding) and the post-processing (isolate-on-black, preview write, thumbnail). `callGemini` and `callQwen` in `electron/processor.ts` are the only places that know the difference, and they are the only part worth testing. DashScope answers with a temporary URL rather than the image, so the Qwen adapter makes a second request to download it; its `watermark` parameter defaults on at DashScope and must always be sent false or every result is defaced. Guarded by the model-choice tests in `electron/processor.test.ts`.
- Alibaba's Qwen keys come in two shapes and the difference is an addressing problem, not a credential one. A key issued since the workspace upgrade begins `sk-ws-` and is only accepted by its own host, `https://{workspace}.{region}.maas.aliyuncs.com/...`; sending it to the shared regional host returns a 401 that reads exactly like a bad key. `qwenEndpoint` builds the address from a stored Workspace ID and falls back to the shared host for older `sk-` keys, `normaliseQwenWorkspace` accepts the id however it was copied (bare, hostname, or whole URL), and `needsQwenWorkspace` names the missing workspace before the request goes out rather than after the 401. The workspace is stored in plain text beside the encrypted keys because it is part of the address, and Test connection saves the field first so it tests what is on screen. Guarded by `shared/models.test.ts`.
- The Qwen model ids are `qwen-image-3.0` and `qwen-image-3.0-pro`, both of which edit. `qwen-image-edit-plus` was taken from pricing pages rather than Alibaba's model list and never existed; a test asserts it now resolves to the default instead of reaching an API. Model ids for a provider must come from that provider's own model list.
- Keys are per provider, one encrypted file each, and the Gemini filename is unchanged so an existing installation keeps the key it already has. `apiKeyStatus` returns one flag per provider so the interface can say which connections are live and which model chips are unusable. Qwen keys are region-bound, and the region is a setting rather than something to detect. Model Studio runs as two separate services — International (Singapore, `dashscope-intl.aliyuncs.com`, workspace hosts under `ap-southeast-1`) and China (Beijing, `dashscope.aliyuncs.com`, workspace hosts under `cn-beijing`) — and a key made in one console is rejected by the other with a 401 that reads like a bad key. Nothing in the key says which it is, so `Model Studio region` sits above the Workspace ID in Settings, is stored in plain text beside it as part of the address, and is passed through `qwenEndpoint`, `aiEdit` and `testConnection`. A stored value that is not one of the two regions falls back to International rather than being pasted into a host name, which is what an older install without the file gets. The rejection message names the region that was tried and tells the user to switch, because that is the actual fix far more often than a wrong key. The default stays International; the user works from mainland China, where the Beijing endpoint is the domestic one and needs no VPN, while Gemini does — a full tunnel sends the Beijing call abroad and back, so split routing by domain is what to advise. Guarded by the region tests in `shared/models.test.ts`.
- IPC channel names are strings on both sides and TypeScript cannot check them: renaming `gemini-edit` to `ai-edit` compiled cleanly while being broken at runtime. Any change to a channel name must be checked against both `electron/preload.ts` and `electron/main.ts`.
- Gemini reconstruction offers editable presets for standard cleanup, full-frame spot removal, cleaning leftover edges, completing cropped artwork, flattening gradient backgrounds, restoring photographed coasters, creating an original reimagining, and a blank custom instruction.
- `Write a prompt for this image` sends the current working revision to a vision model and puts the instruction it writes into the prompt box. It exists because the presets are general by design — the same words for every coaster — and are worth least on the image whose damage, geometry or palette is peculiar to it. The model is fixed at `PROMPT_AUTHOR_MODEL` in `shared/models.ts` (the text sibling of the cheapest image model, sharing the Gemini key): the selector beside the prompt chooses what will redraw the artwork, and making the author of the words a second choice would only add another thing to get wrong. `buildPromptAuthorInstruction` in `src/utils.ts` holds what the model is asked for, and it carries the same house rules the presets do — exact wording, spelling, letterforms, illustration, proportions and printed ink colours preserved; no redesign, no additions — plus the current backdrop decision, including None, which asks for no background colour at all. The target is stated as properties (flat solid colour, crisp unbroken outlines, no photographic surface, texture, glare or shadow, legible small) rather than as a destination, and the garment is named only to the model writing the words: a prompt that says T-shirt gets a T-shirt drawn, so the written instruction is forbidden from asking for a mockup, garment, person, scene, frame or any presentation on a product. The result lands as an ordinary editable prompt and switches the preset to `Custom`, because that is what it now is — leaving it on a preset would let the next preset or backdrop change quietly overwrite it. `cleanAuthoredPrompt` strips a fenced block, a self-introduction or wrapping quotes so the box holds the instruction and nothing else. Guarded by the prompt-authoring tests in `src/utils.test.ts` and the mocked call in `electron/processor.test.ts`.
- `Clean edges` is the fallback for a fringe the deterministic re-composite cannot solve — one smeared across a wide soft ramp, or left where three colours meet, where there is no clean blend of two colours to unmix. Its whole value is that it asks for the fringe and for nothing else: it carries no issue tags, no surround colour, and no fidelity paragraph, because every extra sentence is licence to redraw artwork that only needed its edge tidied. The backdrop squares are disabled while it is selected, as they are for `Complete edges` and `Custom`. Reach for it after `Fill` or `Replace`, not instead of them. Guarded by the clean-edges tests in `src/utils.test.ts`.
- `Complete edges` defaults to at least 2K, detects which original edges are touched by foreground artwork, and adds a dynamically sized area of matching background only on those affected sides before sending the image to Gemini.
- `Complete edges` may continue only shapes already clipped by an original edge. Its prompt must preserve the existing background and explicitly prohibit new text, borders, frames, symbols, logos, characters, objects, scenery, decorations, redesign, or rearrangement.
- The `Photographed coaster` preset targets vintage beer mats, coasters, and bottle labels shot on a table. It asks for three corrections together: square up the camera perspective so the piece returns in its true manufactured shape (a round mat must come back a regular circle, never the ellipse the angle produced); remove age damage such as foxing, stains, scuffs, board texture, glare, and cast shadows; and keep the coaster's own silhouette while filling everything outside it with pure black. Printed rings, borders, and rules are artwork and must be kept; the physical thickness and bevel are flattened away so only the flat silhouette remains. Black is deliberate rather than decorative: it is a known uniform value the user can swap for any colour later with `Replace`, whereas a background extended out of the artwork is baked in and cannot be recovered. The preset must NOT extend the coaster's own background colour outwards — that was an earlier behaviour the user reversed on 2026-08-30. Selecting the preset raises a 1K output to 2K because these sources are around 3000 px. Guarded by prompt tests in `src/utils.test.ts`.
- The `Photographed coaster` preset pads its input out to a square on pure black (`padToSquare`, sent as `GeminiRequest.squareCanvas`) before the request leaves the machine, and its prompt asks for a square image back. This is the fix for a steeply angled shot — `Musée_Européen_de_la_Bière,_Beer_coaster_pic-168.JPG`, 2776 x 2443 — returning as an ellipse on 2026-08-31. Image models take their output frame from the input frame, so a round mat inside an oblong canvas cannot be both a true circle and a full frame, and the model splits the difference. Wording alone had already failed: the prompt demanded a "perfectly regular circle" and "never an ellipse" and still produced one. The padding is the mechanism; the prompt is the intent. Do not reintroduce a same-aspect-ratio instruction to this preset — that clause was the specific thing fighting the geometry, and it is guarded by a negative assertion in `src/utils.test.ts`. Every other preset still returns the frame it was given. Black padding is deliberate: it is the surround the preset already asks for, so the added canvas reads as the target rather than as more table to clean off. Guarded by `electron/square-canvas.test.ts`.
- The coaster prompt states that correct geometry is the highest priority and outranks fidelity to the photographed framing, names the extreme-angle case explicitly (severely foreshortened, almost edge-on, do not merely rotate or partially unskew), demands a circle whose diameter is identical across every axis, and asks for the design's own symmetry back — concentric rings sharing one centre, radial elements evenly spaced and equally sized, curved lettering on true concentric arcs. When photographed appearance and true geometry conflict, geometry wins. Guarded by prompt tests in `src/utils.test.ts`.
- The preset finishes with a deterministic pass (`isolateOnBlack`) that forces everything outside the coaster to exactly `#000000`, because the model returns an approximate black: off-black, vignetted, or with a faint rim around the subject. The surround is found by flooding inward from the frame edge, so the fill stops at the coaster and dark artwork enclosed by the design is unreachable. A leak guard protects the subject: the central fifth of the frame must come back essentially untouched, and a fill covering more than 90% of the frame is rejected, in which case the image is returned unchanged. Refusing is recoverable; a blacked-out image is not. A single centre-pixel test is not sufficient for that guard, since it can land on dark artwork and miss a total leak. Results are written as PNG. Guarded by `electron/isolate-black.test.ts`.
- `Reimagine design` preserves the visual era, mood, palette, and compositional essence while explicitly requesting new wording, original symbols, and non-identical imagery rather than preserving protected identity.
- The Custom preset starts with a blank prompt while still attaching the current working image. When Gemini declines a request, explain the decline and suggest Reimagine design, deterministic local tools, or a source the user has rights to edit.

## Quality and interface

- Every local or Gemini result receives a newly calculated quality score immediately.
- The quality bands are Excellent (85+), Good (70-84), Fair (55-69) and Poor (below 55), and only the ends are coloured: Excellent green, Fair amber, Poor red, Good in the card's own ink. They were High (81+), Medium (55-80) and Low, coloured green, orange and red, which measured over the user's 1352 images painted 62% of the library orange and 10% red — the median image scores 73, so the typical card carried a warning colour, and a warning that fires on the ordinary case is a background rather than a warning. The new bands give 16% green, 46% neutral, 27% amber, 10% red. The edges are not eyeballed: `Good` begins exactly at `QUALITY_RECOMMENDED_SCORE`, so amber and red mean "below the line the workbench itself uses to decide whether a result may replace the original" rather than "below average". That coincidence is the point of the scheme and the two must not be allowed to drift apart — a test asserts they are the same number. `shared/quality.ts` holds the bands, the threshold and `canAcceptQuality` as one definition shared by the process that computes the score and the renderer that colours it; `src/utils.ts` re-exports them. Changing a band changes what `inspectImage` returns, so `SCAN_CACHE_VERSION` was bumped to 2 with it. Guarded by `shared/quality.test.ts`.
- OPEN CONFLICT, raised with the user on 2026-09-06 and not yet resolved: the line below says a result may replace the source only at 81 or higher, but `QUALITY_RECOMMENDED_SCORE` in the code is 70 and the workbench says `Below 70`. The code has been the behaviour for some time and the new bands are anchored to it. Do not quietly change either number: ask which is intended, then move the constant and this line together.
- Quality scoring must measure visible technical fidelity rather than mostly rewarding pixel dimensions or raw edge quantity. Clean flat-colour graphics with crisp boundaries should score highly; blur, colour bleed, ghosted outlines, compression texture, and uneven nominally-flat areas must reduce the score even on a large image.
- Sparse two- or three-colour artwork must not be penalized merely for having calm areas or relatively few edges.
- A modified result may replace the source only when its newly calculated quality score is strictly over 80 (81 or higher). Lower-scoring revisions remain editable and undoable but cannot be accepted.
- After source replacement, rescan and recalculate quality from the saved file. Never continue showing the original score as if it described the result.
- After replacement, close the workbench immediately and refresh only that image's thumbnail, dimensions, hash, and quality in the background. Do not block the collection with a full-screen rescan.
- While that targeted refresh is running, lock only the replaced image card and label it `Updating`; every other image remains available.
- Legacy processed previews are rescored when opened.
- Workbench notifications belong in the unused lower-left footer area so they do not cover the right-side Replace/Use action. Elsewhere notifications may remain bottom-right.

## Required regression checks

Before handing off a change:

1. Run `npm test`.
2. Run `npm run build`.
3. For a user relying on `/Applications/MoodPrep.app`, package and update that installed app; a source build alone does not update it.
4. Confirm the packaged app contains the current renderer asset hashes and main process build.
5. Keep electron-builder output in `release`, never inside the renderer input folder `dist`, to avoid recursive packaging.
6. Package from the installed `node_modules/electron/dist` runtime so release builds do not silently depend on a fresh Electron download.
